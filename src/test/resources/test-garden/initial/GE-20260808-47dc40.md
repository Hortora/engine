### Context

`CasePlanModel` manages plan definitions via several concurrent index
structures: `definitions`, `definitionStates`, `childrenIndex`, `parentIndex`,
`scopedBindings`. Initial decomposition (via `GoalDecomposer`) and plan
adaptation (via `replaceCompound()`) both need to materialise compound
PlanItemDefinitions — but the operations are structurally different.

### The technique

**Do not share a `PlanMaterializer` between initial decomposition and plan
adaptation.** They manipulate different layers of CasePlanModel state:

**Initial decomposition** calls `registerDefinition(compound)` which populates
all index structures in a single operation — `scopedBindings`, `childrenIndex`,
`definitions`, `definitionStates`, `parentIndex` — because the compound is
built with the complete set of bindings upfront.

**Plan adaptation** must REPLACE an existing compound — unregister old children
from all index structures (definitions, definitionStates, childrenIndex,
parentIndex), remove pending PlanItems (preserving completed and running ones),
then re-register the entire compound with updated `scopedBindings`. Using
`addChild()` and `removePlanItem()` alone doesn't work because:

1. `removePlanItem()` doesn't remove child definitions from `childrenIndex` or
   `definitionStates` — orphaned definitions prevent compound completion
2. `addChild()` doesn't update the compound's immutable `scopedBindings` —
   new steps are invisible to `PlanningStrategyLoopControl`'s dispatch loop

### Fix

Use `CasePlanModel.replaceCompound(compoundId, newCompound, generation)` for
adaptation. This method does the full unregister-then-reregister atomically,
including `scopedBindings` replacement via re-registration of the entire
compound definition.

### Why this is non-obvious

The shared-materialisation abstraction seems natural — both operations produce
the same output type (compound with children). The structural difference only
surfaces when you trace through the index data structures that
`registerDefinition()` populates vs what `addChild()` and `removePlanItem()`
actually touch.
